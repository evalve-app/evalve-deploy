# An Experiment of a Loop is a commit and an agent version

Decided 2026-11-16. Story [sc-234](https://app.shortcut.com/team-4-1/story/234). Points 9 and 10 changed on 2026-11-16 with story [sc-327](https://app.shortcut.com/team-4-1/story/327). Points 9, 10 and 13 changed on 2026-11-24 with story [sc-394](https://app.shortcut.com/team-4-1/story/394): one Loop task for each Loop. Points 12 and 13 and two consequences changed on 2026-11-24 with story [sc-471](https://app.shortcut.com/team-4-1/story/471).

In the MVP, each Experiment of a Loop is an override on one pinned agent version, with no git. The target flow ends with a draft PR that a person can merge, so each Experiment must be a real change in the agent repo. We decided that the Teammate's coding agent writes the change, and that the backend checks it, commits it to `loop/<id>` and registers one Kitaru agent version for the commit. We chose this because the backend stays the one owner of the Loop rules and the one writer to GitHub, and it needs no model key.

The terms Loop, Experiment, Control Experiment and Run are in `GLOSSARY.md`. Older text says "Round" for Experiment.

## Decision

1. **Who writes the change.** The Teammate's Claude Code session writes the change for each Experiment and sends it with the Evalve MCP. The backend checks the change, commits it, and starts the Runs. Only the backend writes to GitHub, through the GitHub App. A backend LLM that writes the change ([sc-258](https://app.shortcut.com/team-4-1/story/258)) is parked.
2. **Two stages.**
   * Stage 1 (epic 01): an Experiment is one override, `system_prompt` or `model`, with no git. The Loop rules, the store, the API and the runner are built on this.
   * Stage 2 (epic 05): an Experiment is one commit on `loop/<id>` and one Kitaru agent version for that commit, with `EVALVE_COMMIT=<sha>` in `run.env` and the commit trailer `Kitaru-Experiment: <id>`.
3. **No overrides in stage 2.** In stage 2, a prompt change is a file change only. The `system_prompt` override is removed. The `model` override is not available until the model is in a file on the allow-list.
4. **The format of a change.** The full new content of each changed file, with a one-line reason. Not a unified diff.
5. **Which files a change can touch.** An allow-list of exact paths. The Operator sets the allow-list for the agent. A Loop setup can make it narrower, and cannot make it wider. In v1, each path must be a text file (`.md` or `.txt`) that holds a prompt. The backend refuses each other path, and it refuses a change that the Loop already tried.
6. **Changes do not accumulate.** Each Experiment applies its change to the tree of the base SHA of `loop/<id>`. A failed Experiment keeps its commit and gets a revert commit, whose tree is the tree of the base SHA.
7. **The order for each Experiment.** Find or create the Kitaru experiment, commit with the trailer, register the agent version for the SHA, start the Run. Each step is safe to do again after a restart.
8. **The Control Experiment** is Experiment 0. It has no commit, and it runs the base SHA of `loop/<id>`.
9. **Passing.** An Experiment passes when it has N consecutive green Runs (`required_consecutive_greens`). A Run is green only when it is complete and each session of the cohort version passes each selected binary evaluator. A red Run ends the Experiment. This rule also applies to the Control Experiment. An incomplete Run is not red: it gets a retry. It does not count for the streak, and it does not break the streak. Two incomplete Runs in a row make the Loop `failed` with the outcome `error`. An incomplete Run costs its estimate against the budget. It costs $0 when no worker claimed an agent task of it, and it then still counts for `max_runs` and for the two in a row. A Loop can also become `failed` with the outcome `error` with no Run: when its Loop task has three failed starts in a row, when AWS refuses the start with a 4xx error that is not throttling, or when a failed start cannot succeed in a new attempt (point 13).
10. **End states.** A Loop that stops for one of these reasons has the status `completed` and one outcome:
    * `passed`: an Experiment passed.
    * `already_passing`: the Control Experiment passed. The Loop makes no change, no branch and no PR.
    * `budget_reached`: the budget limit stopped the Loop.
    * `max_runs`: the limit on the total number of Runs of the Loop (`max_runs`) stopped the Loop.
    * `stopped_idle`: the Loop reached the wait limit: it waited for a change for 24 hours. The Loop keeps its branch and gets no PR. `needs_change` is the next action of the Loop, not a status: a Loop that waits for a change has the status `running`. The 24 hours start when the backend collects the last Run of an Experiment. The backend checks the limit when a call arrives, because it has no background task.
11. **The result of a passed Loop** is one draft PR from `loop/<id>` to the default branch. The PR shows a commit and a revert for each failed Experiment, then the commit of the Experiment that passed. The GitHub App cannot merge the PR and cannot mark it ready for review. There is no approval step in the dashboard ([sc-260](https://app.shortcut.com/team-4-1/story/260) is parked).
12. **One agent repo for v1.** The pilot agent repo is [`evalve-app/JavaScript-chatbot`](https://github.com/evalve-app/JavaScript-chatbot). Its prompts are in `backend/app/agents/prompts.py`, which is code. A Loop cannot change them until they are in text files. That move belongs to stage 2. [sc-243](https://app.shortcut.com/team-4-1/story/243) does not do it: it makes the agent image of the pilot agent.
13. **The worker (provisional).** One Loop task on ECS Fargate runs the Runs of one Loop. The terms Loop task, Agent image, Supervisor, Replay, Assignment, Drive, Idle and Failed start are in `GLOSSARY.md`. Each number in this point is a placeholder and a deployment setting. The point stays provisional until a hand test on Fargate has results. The work belongs to the epic "03 Experiments on Fargate".
    * **Unit.** A Loop has one Loop task at a time, and it can have many in sequence. A Loop task serves one Loop only. The Runs of a Loop execute only on Fargate. The backend checks by `worker_id` that the workers of the Loop claimed each agent task and each evaluator task of a Run. A Run that fails the check is incomplete. The purpose is scores that compare, not security, and no network rule enforces it.
    * **Agent image.** The agent gets into the Loop task as one agent image for each commit of the agent: the agent, its locked dependencies, the Kitaru worker and a supervisor, which is Evalve code. One `evalve` command builds and pushes the image, and registers one Kitaru agent version with the digest and the commit. A Teammate and the Operator run the same command, with only a Kitaru API key and no AWS login. For the push, the backend gives the builder an ECR token from a push-only role for the one repository, and the token can live 12 hours; the command registers the agent version and attaches the Kitaru secrets of the agent by name, with the key of the builder. The repository has immutable tags and the push role has no delete, so only the Operator deletes an image. The agent images are data that a restore needs, because a new build of a commit gives a different digest: `evalve up` makes the repository outside Terraform, and it stays after `evalve down` and after the removal of the backend, as the snapshot and the application secret do. `evalve down` also leaves the ECS task definitions. A Teammate can run a Loop on an image that a different Teammate built. The preflight refuses an agent version with no digest, or with a digest that is not in the repository; this is a guard for correctness and does not prove who built the image. The backend registers the ECS task definition of an image inside the driving call that starts a Loop task: one family for each digest, and a new revision when the deployment settings change. The task downloads no source. The build command adds the supervisor as the final layer of the image, from files in the `evalve` CLI: Python with the standard library only, in `/opt/evalve/`, which root owns. The Dockerfile of the team starts from the Kitaru worker image at the version of the server, and the build command refuses an image that does not, a source tree that the worker user can write, and a `kitaru` package that is not at the version of the server. The supervisor, the workers and agent code run as one user that is not root. The task definition sets the entrypoint and the user, so the Dockerfile cannot replace them: `timeout` with the hard lifetime limit, then the supervisor, with an init process. The agent version holds a contract version of the supervisor next to the digest. The preflight and the Assignment route refuse a version that the backend does not support.
    * **Claim.** The supervisor runs one Kitaru worker process for each Replay, limited to the job of that Replay. The backend registers one worker for each job inside the driving call, with the credential of the Loop owner. The Loop task polls the backend for its Assignments, and it shows one secret that is made for each Loop task. A maximum of 10 Replays run at the same time. A Run has a deadline at the expiry of its first worker token (3600 s). After the deadline, the backend cancels the Run and it is incomplete.
    * **Life.** Only a driving call starts a Loop task: first the task, then the Run. A driving call also replaces a Loop task that is not alive while a Run is open. A Loop task is alive when it polled in the last 30 s. It exits by itself after 15 idle minutes, at a lifetime limit of 24 hours, or when its poll is refused. The call that ends the Loop stops the task.
    * **Isolation.** A Replay sees nothing that a different Replay wrote. The Loop task gets this by construction, with no reset step: agent code cannot write the source tree, each worker process has one private directory, and the supervisor kills each leftover process before each Run. Replays share only state that is keyed by its content and that agent code does not write. The purpose is correctness, not security. State outside the Loop task is not isolated: the database of the agent, and tool results on the Kitaru server. For tool results, a Loop permits a `history` tool policy only with the scope `baseline`: a Replay reads only the tool results of the session that it replays, so each Run of a streak reads the same results. The backend refuses the scopes `cohort_version` and `agent`, a `history` policy with no scope or an unknown scope, and the type `llm` when the Loop starts, in the check that refuses `passthrough`. This applies to each Loop, not only to a Loop on Fargate. A write to an imported session between two Runs is not prevented ([sc-441](https://app.shortcut.com/team-4-1/story/441)).
    * **Network.** The Loop task runs in the existing public subnet with a public IP. It calls Kitaru and the backend at the public hostname on port 443. There is no NAT gateway and no VPC endpoint. Egress is TCP 443, plus a list of ports that the Operator sets. The task has no ingress.
    * **Credentials.** The Loop task holds no account credential of Kitaru, has no task role and reads nothing from Secrets Manager. It gets one worker token for each job in its Assignments. The backend has no Kitaru key. The keys of the agent are Kitaru secrets on the agent version. The keys of a judge come only from a provider connection.
    * **Failure.** A failure of AWS gets no outcome of its own. A Run that AWS broke is incomplete (point 9). Three failed starts in a row end the Loop, and a 4xx error from `RunTask` that is not throttling ends it at the first, as does an error when the backend registers the task definition. A failed start that cannot succeed in a new attempt also ends it at the first: an agent image with no supervisor, or a contract version of the supervisor that the backend refuses. One Run can use three Loop tasks. When the third stops, the backend cancels the Run.

## Considered options

* **An LLM in the backend writes the change** (parked, sc-258). A Loop would run with no person and no laptop. Rejected for v1: it adds a model key and a cost source to the backend, and the backend would need the repo content to write a good change. This ADR does not block it, because a backend author would send the same change to the same route.
* **Claude Code commits and pushes with the Teammate's git credentials.** Rejected: the backend could not enforce the allow-list, the trailer or the revert, and each Teammate would need write access to the agent repo.
* **A unified diff as the change format.** Rejected: the backend has no clone, so it would have to fetch each file and apply the diff, and a diff that does not apply is a new failure case. With full content, the allow-list is a path check, the commit is one call to the Git Data API, and the "already tried" check is a hash of the content.
* **An allow-list that the Teammate sets at Loop start.** Rejected: the limit would protect nothing.
* **One one-shot Fargate task for each Experiment, which downloads the agent source** (point 13 until 2026-11-24). Rejected: with overrides only, the code is the same for the whole Loop, so one task pays the image pull one time, and an agent image needs no download and no install at the start. Stage 2 needs a new decision, because each Experiment is then a new commit.
* **A worker that is pinned to the agent version.** Rejected: its `evaluator` claim takes each evaluator task on the server, and two Loops on one agent version take the tasks of each other. Only a job scope limits a worker to one Loop, which is why the agent image holds a supervisor.
* **A private network rule that keeps Runs on AWS** (a private worker endpoint, private subnets). Rejected: it stops laptop workers for all work on the server, and private subnets need a NAT gateway at approximately $33 a month. The backend check gives the same correctness.
* **A background runner in the backend.** Rejected: it needs a new secret and an account that owns each experiment. A coding agent that is disconnected only delays the Loop.
* **A result of its own for a failure of AWS.** Rejected: two Runs in a row with no score show a broken setup, whatever the cause.

## Consequences

* A reviewer sees the full Loop in the PR history. A session traces to a commit, and a commit traces to a Kitaru experiment.
* Only the coding agent of the Loop owner drives a Loop, so a Loop starts no Run while no coding agent is connected. A dashboard session only refreshes it. The wait limit in point 10 ends a Loop that nobody continues.
* **Security.** Agent code runs in the Loop task. It can read the worker token of its Replay and the secret of the Loop task. A worker token can also read each job and download each blob by its ID. The Loop task holds no account credential and no AWS role. This is acceptable because an Experiment is only an override on one pinned agent version, and in stage 2 because of the allow-list of prompt text files (the secrets ADR, story [sc-233](https://app.shortcut.com/team-4-1/story/233)). A wider allow-list, or a prompt in a code file, reopens both ADRs.
* The backend stores the worker tokens of the open Run in plain form, and the secret of the Loop task is in a `RunTask` override. The pilot accepts the two.
* The Operator upgrades the Kitaru server only when no Loop runs, and then builds the agent image again.
* The pilot accepts three limits of the agent images. An ECR push token can live 12 hours. Each Kitaru account can change or delete the agent version of a different account. Nothing limits the number of agent images.
* A worker that the backend registered in Kitaru and did not store stays there with a token that nobody holds. It claims nothing, and nothing deletes it. The `worker_id` check reads only completed tasks, so a foreign worker that claimed a task and stopped before the end leaves no trace.
* The store and the API get two new outcomes, `already_passing` and `stopped_idle`. They get no new status. The outcome `passed` replaces `target_reached`, and the outcome `no_improvement` is removed, because no rule gives it.
* The passing rule differs from the `evalve-loop` skill script (`loop.py`) in two cases. In `loop.py`, the control lap continues after a red run, and an incomplete run breaks the streak.
* The term "Round" goes out of use. The MCP tool `propose_round` becomes `propose_experiment`, and the stories and the Loop API change their wording.
* Revisit when the hand test on Fargate has results (point 13), when a Loop must run unattended, when a Loop must change code or the model in stage 2, or when a second agent repo is necessary.
