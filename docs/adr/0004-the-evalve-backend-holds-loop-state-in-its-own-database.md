# The Evalve backend holds Loop state in its own database

Decided 2026-11-16. Story [sc-232](https://app.shortcut.com/team-4-1/story/232). This ADR replaces ADR 0002.

Updated on 2026-11-18 by [sc-378](https://app.shortcut.com/team-4-1/story/378): `evalve up` deploys the backend digest pinned in `DEFAULT_BACKEND_IMAGE` without a flag. A second variable, `backend_image_pinned`, records when an Operator pins another image by hand.

ADR 0002 said that Evalve deploys no Loop state API, because Kitaru stores all that an MVP Loop needs. The epic [01 Agent-driven Loops on AWS](https://app.shortcut.com/team-4-1/epic/26) changes that: a Teammate's coding agent runs a Loop through the Evalve MCP, and one service must own the Loop rules and keep the state between calls. Kitaru cannot hold that state. We decided to run the Evalve backend as a container on the existing EC2 host, with its own database on the PostgreSQL server of Kitaru, and with no credential of its own for Kitaru. We chose this because it adds one container and one database to the deployment, and no host, no secret and no account.

The terms Loop, Experiment, Run and Evalve backend are in `GLOSSARY.md`.

## Decision

1. **Where the backend runs.** A container on the existing EC2 host, with `--network host`, bound to `127.0.0.1:8100`. Caddy sends `/evalve/*` to it. The IMDS hop limit stays 1. The host stays a t3.small. The memory spike [sc-236](https://app.shortcut.com/team-4-1/story/236) can change the host size.
2. **Where Loop state lives.** A separate database named `evalve` on the existing RDS instance of Kitaru. The backend creates the database at startup if it is missing. The migrations of Kitaru never touch it, and the backend never touches the database of Kitaru.
3. **Database credentials (interim).** The backend uses the PostgreSQL user of Kitaru, from the existing application secret. The secrets ADR ([sc-233](https://app.shortcut.com/team-4-1/story/233)) decides the final credentials.
4. **Restore and `down`.** One RDS snapshot holds the database of Kitaru and the `evalve` database at the same point in time. The backend leaves a restored `evalve` database as it is. Restore and `down` have no special step for Loops: a Loop that was `running` in the snapshot continues on the next call.
5. **Which repo holds the backend code.** [`evalve-app/evalve-backend`](https://github.com/evalve-app/evalve-backend). A `v*` tag publishes the public image `ghcr.io/evalve-app/evalve-backend`. `evalve-deploy` pins the image by digest, as it pins the server image. The same repo publishes the local Evalve MCP as a second package. The MCP calls the backend over HTTP and never runs on AWS.
6. **How the backend checks a caller.** On each request to a route that needs a caller, the backend sends the caller's Bearer credential (a `KITKEY_` key or a Kitaru token) to Kitaru `GET /api/v1/accounts/me`. It never stores or logs the credential. A missing, invalid or expired credential, or a deactivated account, gets 401. If Kitaru cannot answer, the caller gets 503 on each of those routes. `GET /evalve/health` is not one of them: it needs no credential, it makes no call to Kitaru, and it stays available when Kitaru is down. The backend does not cache the answer, so a revoked key or a deactivated account stops at the next request. The backend accepts a key and a token in the same way, and it accepts each active account: an Admin account and a service account have the same rules as each other account. The dashboard signs in with its Kitaru session and not with a Bearer credential (decided 2026-11-17, story [sc-350](https://app.shortcut.com/team-4-1/story/350); the story [sc-284](https://app.shortcut.com/team-4-1/story/284) builds it). The backend reads the session cookie and sends it to Kitaru as a cookie, together with the `X-CSRF-Token` header of the caller. It does not send the cookie value as a Bearer credential, because Kitaru does the CSRF check only for a credential that comes from a cookie. Thus Kitaru refuses a session with a missing or wrong CSRF token on each request, also on a GET, and the backend has no CSRF check of its own. This check and the `SameSite=Lax` attribute of the cookie are the protection against cross-site requests. If a request has an `Authorization` header and the session cookie, the header is the credential and the backend ignores the cookie, as Kitaru does. The name of the cookie is the setting `EVALVE_SESSION_COOKIE_NAME` of the backend. The deployment sets it to the name that it gives to Kitaru (`evalve_session`), and an empty value turns cookie sign-in off. A dashboard session has the same rules as a key or a token on each route. No route treats the two differently.
7. **Which identity the backend uses for Kitaru.** The caller's credential, on each request: the key, the token, or the dashboard session (the cookie with the CSRF token). Where this ADR says "the caller's key", a dashboard session is used in the same way. The backend has no Kitaru key of its own, so each Kitaru experiment belongs to the Teammate. The backend does no work with no caller attached. A service account ([sc-287](https://app.shortcut.com/team-4-1/story/287)) comes with the epic "Experiments on Fargate", when the backend must work in the background.
8. **What the backend holds in this epic.** Loop state only: the Loop, its Experiments and their Runs. It holds no AWS credential of its own, no GitHub credential and no approval record. Those come with the later epics and with the secrets ADR.
9. **What a caller is allowed to do** (decided 2026-11-17, story [sc-313](https://app.shortcut.com/team-4-1/story/313)). The backend reads the agent, the cohort version and the evaluators of a Loop with the caller's key, and that read is the only check. Kitaru lets each account read and change each resource, so the backend adds no stricter rule: a Teammate can start a Loop on an agent that a different Teammate made. Each active account can read each Loop: the list, the status, the evidence of a Run and the report. Only the Loop owner can change or cancel a Loop. Each other account gets 403 on those two routes, and an Admin account is not an exception. A read by an account that is not the Loop owner uses the Loop store only: it makes no call to Kitaru apart from the identity check, and it does not move the Loop. Until 2026-11-17, this point said that only the Loop owner could read a Loop, and that each other account got 404.

## Considered options

* **A Loop state API module in `evalve-deploy`** (the fallback in ADR 0002). Rejected: the backend has its own release cycle, and a deploy tool must not hold application code.
* **A schema in the database of Kitaru.** Rejected: the migrations of Kitaru own that database, and a Kitaru upgrade could change or remove tables that it does not know.
* **A second RDS instance.** Rejected: it adds cost and a second backup that must stay in step with the first.
* **A file on the host (SQLite).** Rejected: each change of the dashboard step replaces the EC2 instance, and the file would go with it.
* **A separate host or a Fargate service for the backend.** Rejected for now: it adds cost and a network path for a service that only answers calls.
* **A Kitaru key or service account for the backend.** Rejected for this epic: it is a new secret, and each experiment would belong to the backend and not to the Teammate. It becomes necessary when the backend works in the background (sc-287).

## Consequences

* **The backend container can read the credentials of the instance role.** With the host network, IMDS is one hop from the container. The Kitaru and UI containers cannot reach IMDS. This is acceptable only because the backend runs Evalve code and never agent code. Do not run agent code in this container.
* **The backend can read and write the tables of Kitaru** while it uses the PostgreSQL user of Kitaru (point 3). The code does not do so. The secrets ADR must close this.
* That PostgreSQL user must be allowed to create a database.
* A Loop moves only on a call from its Loop owner. A run in flight finishes in Kitaru, and the next call from the Loop owner collects it. A different account that reads the Loop gets the stored state, which can be older than the state in Kitaru.
* Each active account can read the setup, the prompt text of each change and the evidence of each Loop. This shows no more than Kitaru shows, because each account can read each experiment there.
* Each request to a route that needs a caller costs one call to Kitaru `/accounts/me`. The call stays on the host, and Kitaru has no rate limit. If Kitaru is down, the backend refuses each of those requests with 503, also a status call that needs only the Loop store. The health route is the exception (point 6). Add a cache only if a measurement shows that the call slows the polls.
* The Loops of a deactivated account stay in the database. Each account can read them, and no account can change or cancel them. A Loop that was `running` stays `running`, because the idle limit applies only when a call from the Loop owner arrives. It spends nothing after its run in flight finishes. A reactivated account continues its Loops.
* Two accounts cannot have a Loop with the same name on one agent at the same time, because Kitaru experiment names are unique for each agent. The refusal shows the second account that the name is in use.
* The Operator has no Loop route to stop the Loop of a different account. The Operator can cancel the run in Kitaru: two incomplete Runs in a row make the Loop `failed`.
* Caddy gets one route, `/evalve/*`, before the dashboard route. The deployment gets one optional systemd unit and one image variable (`backend_image`). The story [sc-246](https://app.shortcut.com/team-4-1/story/246) builds them.
* `evalve up` can check the running build, because `GET /evalve/health` returns the image reference.
* Revisit when the backend must work in the background (sc-287), when it gets AWS or GitHub credentials, when the memory spike sc-236 has results, or when the secrets ADR sets the database credentials.
